Canvas is maintained by one person. These rules keep review possible and keep the project safe for the people who run it.

## Before you write code

1. Open an issue (Bug or Idea) and wait for a reply. Pull requests without an issue the maintainer agreed to are closed without review, however good they are.
2. Keep one change per pull request. A pull request that touches many unrelated files is closed.
3. Ask before adding a dependency. Every package is code that runs on users' machines; most changes need none.

## What a pull request must have

- A linked issue and a short description of what changes and how you checked it.
- `pnpm typecheck`, `pnpm test` and `pnpm qa` passing on your machine (see [docs/developer-guide.md](docs/developer-guide.md) for the setup). For anything in the macOS shell, `pnpm qa:native` too.
- A test that fails without your change and passes with it.
- A screenshot for anything you can see.

## What is never accepted

- Binaries, archives, fonts, compiled or minified code, or code generated by a tool you did not review line by line.
- Changes under `.github/` (CI, the PR guard, code owners). Only the maintainer changes those.
- Install-time scripts (`postinstall` and friends) or changes to `pnpm-workspace.yaml`.
- Code that sends data anywhere off the machine without the user turning it on.
- Changes you cannot explain line by line. Using an AI tool is fine; submitting what it wrote without reading it is not.

## How pull requests are checked

Assume every pull request is reviewed as if it came from someone trying to sneak something in. That is not personal; it is how open projects stay safe.

- **CI** (`.github/workflows/ci.yml`) runs typecheck, unit tests and the engine and shell tests. It runs with a read-only token and no secrets, and for outside contributors it waits until the maintainer approves the run.
- **The PR guard** (`.github/workflows/pr-guard.yml`) reads the diff without running any of it and fails on binaries, install scripts, `.github/` changes, minified lines and hidden Unicode. It runs from main's copy, so a pull request cannot switch it off.
- **Review.** Every pull request needs the maintainer's approval (`CODEOWNERS`), after the last push. Dependency, build-script, MCP and server changes get a line-by-line read.
- **main** cannot be force-pushed or deleted, and changes reach it only through a reviewed pull request.

## Performance gate

Run `pnpm perf:gate` on a quiet machine with the engine built. The release checklist runs
the gate too. Its `--quick` option runs the server and page measurements only.
For the native measurements, build an isolated QA app from the current sources first.

```sh
QA=1 CANVAS_APP_OUT="$PWD/build/perf-native/Canvas QA.app" bash apps/macos/build.sh
```

The gate uses fixed fixtures, a warm-up, and the median of three samples. It reports the
spread and retries a metric once if the range exceeds 5% of the median. A result more
than 5% above its budget fails. A stable improvement greater than 3% tightens the budget.
Review and commit any updates to `bench/budgets.json` with the change that was measured.

Use `pnpm perf:gate --only open-2000,server-memory` to check individual metrics.
A missing machine class or budget needs the maintainer. Use `--update` to register a
separate machine class or accept an intentional trade-off. The native metrics are skipped
on machines without the QA app build.
